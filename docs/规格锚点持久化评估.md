# 规格锚点持久化：评估与实施路径

> **代码基线**：本阶段提交。结论先说：**本轮实现「可无损带走」的能力，不接进 SQLite。**
> 接持久化会改变「服务重启 = 新会话」这个产品语义，属于要单独拍板的行为变更，
> 不是一个可以顺手补上的技术缺口。本文把判据、改动面、风险和验收标准写清，
> 免得下次会话又从「要不要做」重新吵一遍。

## 1. 现状是什么

批次 4（`2a37a09`）给 `yxcore/session.py` 加了规格状态机：

- `state`：用户说过、当前要求生效的补丁表（**未必算通过**）；
- `_verified`：最近一份真排出过方案的 `SpecSnapshot`（补丁表 + 规划时点、时点来源、
  告警水位线、输入哈希、基座、规格键）；
- `_verified_history`：按版本记的规格台账，支撑「回到上一版」；
- `run()` 只有求解成功才定稿，失败撤回到上一份已验证规格，说明留在 `last_rollback`。

这些字段全跟着 `YxEngine` 实例活在 `AgentRuntime._yx_engines`
（`agent_runtime.py` 的进程内字典）里。**服务重启、换实例、或者这个字典被清掉，
「哪份要求算数」就回到空白。** README「已知限制」已如实写明，它不是 bug。

## 2. 本轮做了什么（有实测证据）

存储侧本来就有现成的东西，不用新造轮子：

- `backend/app/core/conversation_memory.py` 的 `ConversationMemory` 有
  `state: dict[str, Any]`，整份 JSON 存在 SQLite 的 `conversation_memory.payload`；
  `ConversationMemoryRepository.upsert()/get()` 已经可用。
- `SpecSnapshot.to_dict()` 本来就能把一份规格序列化成纯数据。

缺的是**反序列化**。实测 `Patch.to_json()` → `parse_patch()` 在三类补丁
（计数上限、任务清单排除、数据层增量）上**完全无损**。于是补上了这块：

| 新增 | 作用 |
|---|---|
| `Session.export_spec()` | 把当前要求、已验证规格、规格台账、最近失败说明、基座、轮数导成纯数据 |
| `Session.import_spec(payload)` | 恢复上述状态；任何一处解码失败就**整份拒绝**，不半恢复 |
| `yxcore/tests/test_session.py` 3 条用例 | 往返无损（含 2 版台账 + 未验证改动 + 失败说明）、坏数据整份拒绝、空会话往返 |

**明确没做**：没有调用 `memory_repo.upsert()`，没有在 `_yx_engine()` 里自动恢复，
没有改任何运行时行为。线上行为与本阶段之前完全一致。

### 一个必须写清的边界

`turns` 是逐轮对话记录，不属于规格状态，只把轮数当审计信息导出、不还原对话记录。
而 `fingerprint()` 把轮数算进去了，所以**恢复后的会话指纹不等于导出前的指纹**。
将来接持久化时，不能拿 `fingerprint()` 当「跨重启是不是同一份状态」的判据。
这也是测试里不断言指纹相等、而是断言 `spec_trace()` 与 `state` 相等的原因。

## 3. 真要接，需要动哪些点

四个 `engine.session.run(seconds=_SOLVE_SECONDS)` 入口，**性质不一样，不能一刀切**：

| 位置 | 会话来源 | 该不该持久化 |
|---|---|---|
| `_run_batch_scenario_sync` | 现场 `YxEngine()`，多方案对比里 fork 的一次性会话 | **不该**，算完即弃 |
| `_execute_batch_job` | 现场 `YxEngine()`，批量任务的一次性会话 | **不该**，算完即弃 |
| `_yx_run_sync` | `self._yx_engine(cid)`，按会话缓存的主链路 | 该 |
| `_execute_job` | `self._yx_engine(cid)`，后台求解任务 | 该 |

具体改动面：

1. **写回时机**：`Session.run()` 成功定稿后、失败回滚后都要写。不能只写成功那份，
   否则重启后状态回到「没验证过的改动」被当成已生效。所以最好在
   `agent_runtime` 里包一层统一的 `_run_with_persistence(cid, ...)`，
   把 4 个入口里的 2 个持久会话收进去，一次性 `try/except/finally` 处理。
2. **恢复时机**：`_yx_engine(cid)` 新建 `YxEngine` 时，从
   `memory_repo.get(cid)` 读 `state["规格锚点"]`，调 `session.import_spec()`。
   读不到或坏数据要静默当新会话（有 `import_spec` 的拒绝说明可记日志），
   **不能让一份旧快照把服务启动卡住**。
3. **缓存键冲突**：`ConversationMemoryCache` 是按 `messageCount` 命中
   （消息数没变才复用）。规格状态变化不伴随消息数变化，直接 `upsert`
   可能与缓存里的旧副本互相覆盖。接线时要决定是让规格写绕过缓存、还是
   让写入同时刷新缓存。
4. **并发**：`_execute_job` 在线程池里跑，同一个 `conversation_id` 可能同时有
   同步主链路和后台任务写状态，`memory_repo.upsert` 是整份覆盖，需要串行化或
   加版本戳，否则后写的会盖掉先写的。

## 4. 为什么本轮不接

1. **它改的是产品语义，不是补一个技术缺口。** 现在是「重启 = 新会话、从空白开始」；
   接完变成「重启后接着上一份已验证规格继续」。用户没意识到发生过重启时，
   会以为系统记得更久、也可能困惑于「为什么新的一天还在按旧台账算」。
2. **线上刚发布完**（`2a37a09` 的部署包已上线并实测），改会话生命周期要重新
   构建部署包、重跑全量回归、再发布一次。这不该夹在一轮「把清单清干净」里顺手做。
3. **README 已经把它写成已知限制**，且 `spec_status()` 现在会标「事实层已推进」、
   只提示不自动重排。恢复一份跨天的旧规格后，这套提示是否正确、
   要不要联动重排，本身就是一个需要定口径的问题。
4. 用户此前明确「不要增加没必要的代码」「不希望到处是补丁」。在没有明确要
   「跨重启记住」这个需求之前，先把可序列化能力备好、把决策依据写清，比先接上
   再回滚更省事。

## 5. 推荐实施方案（要做得按这个走）

**第一步：接线 + 开关**。按 §3 的 4 点改 `agent_runtime.py`，加环境变量
`SPEC_ANCHOR_PERSIST=1` 控制，默认关闭。演示站与本地默认行为不变。

**第二步：验收**。至少补这些测试，再加一次真实两轮对话 + 重启恢复：

- 导出 → 新进程导入 → `state` / `spec_trace()` / `spec_status()` 一致；
- 求解失败写回后重启，不能把没验证过的改动当已生效；
- 坏数据 / 旧格式版本不阻塞启动，按新会话处理；
- 两个会话并发写，不互相覆盖；
- 跨天恢复：`spec_status()["事实层已推进"]` 为真、提示出现、方案未被自动重排；
- 一次性 batch 会话不产生任何持久化写入。

**第三步**：全量回归 + 重建部署包 + 发布，并从 README「已知限制」里移除这一条，
改为指向本文与实现。

## 6. 风险清单（接线时要逐条回答）

| 风险 | 说明 |
|---|---|
| 事实层推进 | 规格带 `as_of` / 水位线；恢复后台账可能已往前走，旧方案不能直接和新方案比成本 |
| 指纹含轮数 | 见 §2 边界，不能当跨重启等价判据 |
| 额度与隐私 | `conversation_memory` 里会多存一份用户要求表；要确认它和现有会话记忆的保留策略一致 |
| 演示 vs 生产 | 演示站钉在 `PLANNING_AS_OF=2026-11-08`，生产跟随当天；跨重启恢复在两种部署下的表现不同 |
| 版本演进 | `SPEC_FORMAT` 现在是 1；将来字段变了要有迁移或明确拒绝旧版本 |

## 7. 什么时候该做

判据不是「技术上能不能」，而是**有没有真实需求要求跨重启继续同一份规格**。
出现下面任一条，就该排期：

- 用户明确说「昨天聊到哪今天接着来」；
- 部署从单实例变成多实例，同一会话可能落到不同进程；
- 服务频繁重启，用户反复丢失「回到上一版」的历史。

在出现之前，保持「重启即新会话」这个诚实、可预期、无需额外状态的行为。
